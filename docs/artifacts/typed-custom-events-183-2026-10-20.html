Typed Custom Events

You can emit() a custom event, but you can't on() it. Filed July 21 against 6.x. The repo has had 76 commits and four releases since. Here is where it stands and what to do about it.

Still an issue?
Yes, unchanged

Same TS2769 on both createFsm and createBehavioralFsm. Nothing since July touched on(). The events guide now documents the wildcard-and-cast workaround as the official path.

A less intrusive fix?
Yes: two layers

Layer 1 widens on(), adds nothing to the config or the factories, and closes the complaint for everyone. Layer 2 adds an opt-in event map that types both halves. One decision is yours: where the map gets declared.

Found during review
🔥 Relay strips client

An Fsm removes any client key from custom payloads, not just built-ins. Typed events would make that lie visible, so it needs a fix first.

Three surfaces, two opinions

The private emitter and the React adapter already accept any string. Only the public on() overloads on the two classes refuse. Layer 1 is the public surface agreeing with the other two.

Private emitter wide

Proposal

Layer 1ship regardlessminor bumptype-only

Widen on() so any string subscribes, with unknown for undeclared names

Key the on<K> overload by keyof (FsmEventMap<S> & Record<string, unknown>). Built-in names keep their narrowed payloads because the intersection resolves them first. Any other string resolves to unknown. Declare the "*" overload before the keyed overload so "*" never falls into the index signature.

  • It does not touch the class generics or the config type. The change is the on() overloads in fsm.ts and the same edit in behavioral-fsm.ts.
  • Closes the issue's literal complaint for JS users, the untyped path, and anyone who never declares a map.
  • Strictly removes a false error. No existing call becomes invalid.
Layer 2opt-inminor bumptype-only

An event map that types emit in handlers and on on the instance

The contract is the input payload map's. The engine never reads the type. You declare it once, and the compiler checks emit and on against it. The pieces:

  • EventMap = Record<string, unknown> and EventMapLike<T>, mirroring InputMap / InputMapLike for the same reason (a named interface has no index signature).
  • Sixth class generic on Fsm and BehavioralFsm: TEvents extends EventMapLike<TEvents> = EventMap. Default reproduces Layer 1 exactly.
  • HandlerArgs<TCtx, TStateNames, TEvents = EventMap>: emit<K extends keyof TEvents & string>(name: K, ...data: EmitArgs<TEvents[K]>). Under the wide default it degenerates to today's emit(name: string, data?: unknown). Payload is optional only when the declared type admits undefined.
  • on() keyed by FsmEventMap<S> & TEvents (or BehavioralFsmEventMap<C, S> & TEvents). Built-in names win on collision.
  • EventMapOfInstance<TFsm> extractor, so machina-react's useFsmEvent can offer custom names in a follow-up.

Compared with Layer 1, emit("sya") becomes a compile error. A payload that does not match the declared type becomes a compile error. Subscribers get the declared type without a cast. Every assertion held in the spike (see Evidence).

Code, four ways

// The existing slot accepts EITHER an input map (8.0 form, unchanged)
// OR a bag with named members. No ladder, no placeholder.
const a = createFsm<ConnectivityInputs>()({ ... });                       // 8.0, untouched
const b = createFsm<{ events: ConnectivityEvents }>()({ ... });            // events only
const c = createFsm<{ inputs: ConnectivityInputs; events: ConnectivityEvents }>()({ ... });

// Behavioral: TClient stays first because it is required information,
// not a placeholder. Everything after it is one named bag.
const conn = createBehavioralFsm<Connection, { events: ConnectionEvents }>()({ ... });

// How the slot tells them apart (verified in the spike):
// an input map's values are all tuples; a bag's members are object maps.
type IsInputMap<T> = T extends InputMapLike<T> ? true : false;
type InputsOf<T>  = IsInputMap<T> extends true ? T        : T extends { inputs: infer I } ? I : InputMap;
type EventsOf<T>  = IsInputMap<T> extends true ? EventMap : T extends { events: infer E } ? E : EventMap;

// Edge: an input map with an input literally named `inputs` (tuple payload)
// is still an input map. The discriminator is the value type, not the key.
type Weird = { inputs: [n: number]; events: [] };
createFsm<Weird>()   // InputsOf = Weird, EventsOf = EventMap

The library keeps one declaration convention and the 8.0 docs stay correct. The class generics are unchanged. typeof createBehavioralFsm<Client, X> keeps binding X to the same position, which is the exact break that made 8.0 a major. The slot's constraint becomes a union. A malformed bag then reports TS2344 on the type argument, the same error a malformed input map reports today.

// examples/connectivity/src/main.ts, as shipped today
const wildcardSub = fsm.on("*", (eventName: string, data: unknown) => {
    if (eventName === "checkCountUpdated") {
        const { checkCount } = data as { checkCount: number };
        renderCheckCount(checkCount, MAX_CHECKS);
    }
});

// What the user wanted to write:
fsm.on("checkCountUpdated", (data) => { /* ... */ });
// error TS2769: Argument of type '"checkCountUpdated"' is not assignable to
//   parameter of type '"transitioning" | "transitioned" | ... | "deferred"'.

Every subscriber re-does the dispatch the emitter already did, then casts. The events guide documents this as the way to do it.

// fsm.ts (BehavioralFsm gets the same edit with its own map)
on(eventName: "*", callback: (eventName: string, data: unknown) => void): Subscription;
on<K extends keyof (FsmEventMap<TStateNames> & EventMap) & string>(
    eventName: K,
    callback: (data: (FsmEventMap<TStateNames> & EventMap)[K]) => void
): Subscription;
on<K extends keyof FsmEventMap<TStateNames> & string>(
    eventName: K, callback: (data: FsmEventMap<TStateNames>[K]) => void
): Subscription;
on(eventName: "*", callback: (eventName: string, data: unknown) => void): Subscription;

// Caller
fsm.on("transitioned", ({ fromState }) => { ... });   // fromState: "online" | "offline" | "checking"
fsm.on("checkCountUpdated", (data) => { ... });        // data: unknown, compiles
fsm.on("*", (name, data) => { ... });                   // unchanged

The "*" overload moves first. With the index signature in play, "*" would otherwise match the keyed overload for a one-argument callback.

type ConnectivityEvents = {
    checkCountUpdated: { checkCount: number };
    maxChecksReached: undefined;              // no payload
};

// Second curried slot, after the input map. Same shape as #195.
const fsm = createFsm<ConnectivityInputs, ConnectivityEvents>()({
    id: "connectivity",
    initialState: "online",
    context: { checkCount: 0 },
    states: {
        checking: {
            _onEnter({ ctx, emit }) {
                emit("checkCountUpdated", { checkCount: ctx.checkCount }); // checked
                emit("maxChecksReached");                                   // payload optional
                emit("checkCountUpdate", {});   // error: not in the map
            },
        },
    },
});

fsm.on("checkCountUpdated", ({ checkCount }) => renderCheckCount(checkCount)); // typed
fsm.on("transitioned", ({ toState }) => ...);                                  // still typed

// Events only, no input map. Type arguments are positional, so the
// input slot needs a placeholder to reach the events slot:
const light = createFsm<InputMap, TrafficLightEvents>()({ ... });

// createBehavioralFsm is worse. TClient is required (it is why the curry
// exists), and the input placeholder sits between it and the events:
const conn  = createBehavioralFsm<Connection, InputMap, ConnectionEvents>()({ ... });
//                                 ^ required    ^ placeholder  ^ what you wanted

Consistent with the 8.0 rule that currying is forced, not styled. The cost is the positional ladder. TypeScript has no named type arguments and no way to skip one, so every map before the one you want becomes a placeholder. On createBehavioralFsm that is two arguments of ceremony for one map.

// Inferred from a config property, like `context` infers TCtx.
// Works on the direct form AND the curried form, no ladder.
const fsm = createFsm({
    id: "connectivity",
    initialState: "online",
    context: { checkCount: 0 },
    events: {} as ConnectivityEvents,      // phantom value; engine never reads it
    states: { ... },                        // emit typed inside handlers, same as above
});

fsm.on("checkCountUpdated", ({ checkCount }) => ...);  // typed

// Optional sugar to hide the cast:
events: eventMap<ConnectivityEvents>(),   // returns {} as T

XState v5 does exactly this with setup({ types: {} as {...} }). XState has used it in production since v5, and it reads well. The cost is a runtime key whose value is a lie, and a second way to declare a type-only map next to the curried one you just shipped.

Considered and set aside

OptionWhy not
Infer the map from emit() call sitesTypeScript does not infer type parameters from calls inside a function body. Handler bodies are context-sensitive and checked after inference settles, so there is nothing to infer from.
Per-call generic: fsm.on<{ line: string }>("say", cb)Trust-me typing. The subscriber asserts a type nothing verified. emit stays untyped, so the typo class the issue cares about survives.
Typed view helper: typedEvents<MyEvents>(fsm).on(...)It leaves the classes and factories untouched, but it types only the subscribe half, the mirror image of today's problem.
Builder chain: createFsm().inputs<I>().events<E>()(cfg)Named, no ladder, but a function-with-properties return type is harder to read in hover text and in errors than one slot, and it is a third calling convention for the same factory.
Issue's fallback: add on(eventName: string, cb: (data: unknown) => void)Equivalent to Layer 1 in effect, but a third overload on top of two. Keying the existing overload by the wide map is the same result in fewer signatures, and it is what the private emitter already is.

Impact by layer

Layer 1 + relay fix

  • packages/machina/src/fsm.ts: reorder and widen the on() overloads. The relay strips client only for built-in names.
  • packages/machina/src/behavioral-fsm.ts: same on() edit.
  • types.ts: export EventMap.
  • instance-types.test.ts: pins that prove built-in payloads stay narrowed once on() accepts any string, that a custom name compiles with unknown, and that the wildcard signature is unchanged.
  • fsm.test.ts: relay test for a custom payload with a client key.
  • Docs guide/events.mdx: rewrite "Custom events" and "TypeScript". Examples: connectivity and shopping-cart drop the wildcard filter.

Layer 2 adds

  • types.ts: EventMapLike, EmitArgs, EventMapOfInstance; HandlerArgs and HandlerFn gain a defaulted TEvents. FsmConfig threads it to handlers and onDispose.
  • Both classes: sixth generic. Compat pins for 3-arg and 5-arg annotations must still pass (defaults make this additive).
  • Factories, per decision 1. Bag: widen the slot's constraint to InputMapLike<T> | Vocab and route InputsOf / EventsOf into the return type. Config property: add events?: TEvents to FsmConfig. Positional: one more defaulted type argument on each factory.
  • index.ts: export the new types.
  • Docs guide/typed-payloads.mdx: a "Typed events" section beside the input map.
  • Follow-up PR in machina-react: FsmEventName<TFsm> unions keyof EventMapOfInstance<TFsm>.

Both layers add types only. The relay fix is the one change to engine behavior. One minor release (8.2.0) covers both. Split the work into a Layer 1 PR, which is small and uncontroversial, and a Layer 2 PR, which carries the decision.

⚠️ One thing to verify during implementation, not design. The five *OfInstance extractors use positional infer lists. They kept working when 8.0 added the fifth generic because unlisted parameters fall to defaults. A sixth should behave the same. The pin suite is the proof, not this page.

this.bfsm.on("*", (eventName, data) => {
    if (data && typeof data === "object" && "client" in data) {
        const { client: _, ...payload } = data as Record<string, unknown>;
        (this.emitter as any).emit(eventName, payload);   // custom events take this branch too
    } else { ... }

fsm.emit("assigned", { client: "acme", seat: 3 });

Built-ins are the only events the engine stamps client onto, so the relay should key on the event name, not on the payload's shape.
