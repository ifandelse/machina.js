---
title: Migrating from v6 to v7
description: v7 tightens compile-time validation and extends hierarchical delegation to any depth, with new bubbles declarations. The runtime API is nearly unchanged, and the compiler reports new type errors in some previously-compiling code.
---

v7 is a small migration with one catch: some code that compiled under v6 stops compiling, and in almost every case that code was already broken and v6 didn't report it. The runtime API is unchanged except for one deliberate fix to `canHandle()`.

## New compile errors you might see

**Configs with an empty state or a function-only state get checked now.** With v6, a state that was an empty object (`{}`), or far more commonly a state containing only unannotated handler functions such as an unaccompanied `_onEnter`/`_onExit`, silently disabled literal-type validation for the whole config. Shorthand transition targets, `initialState`, `handle()` input names, and `defer({ until })` all accepted any string. v7 validates each config form.

What to do: read the new errors. Each one points at a latent bug, such as a typo'd state name or an input nothing handles. Fix the typo, because the code was never doing what it looked like it did.

**`defer({ until })` only accepts real state names.** Typos get a "Did you mean" suggestion. If you had a handler annotated with an explicitly widened defer signature (`defer: (o?: { until: string }) => void`), it no longer compiles. Annotate the args object as `HandlerArgs<YourCtx>` instead, or just destructure without annotations and let inference do it.

**Where shorthand-typo errors anchor varies.** Depending on the structure of neighboring states, TypeScript reports the error on the state object's line or on the property itself. Either way the error chain states the exact property. If the first line looks broad, read past it.

## The one runtime change: delegation reaches any depth

Under v6, `canHandle()` checked one level: the current state's own handlers plus its `"*"`. A parent delegating to a child stopped there: an input handled by a grandchild behind a handler-less middle FSM was unreachable from the root and dead-ended as `nohandler`. Under v7, `canHandle()` answers for the whole `_child` chain, and `handle()`'s delegation follows it all the way down.

The shifted behaviors are consistent with the child-first precedence machina always had one level deep, and with how UML/SCXML/XState statecharts resolve events (innermost active state first):

- Inputs that previously dead-ended as `nohandler` at an ancestor are now handled by the descendant that declares them. If you had `nohandler` listeners doing real work for those inputs, they'll fire less often.
- A deeper descendant's handler now takes precedence over an ancestor's local handler for the same input name. A handler-less middle FSM no longer "shields" an ancestor handler. Give such inputs distinct names per level, or drive the ancestor directly with `transition()`.

## New capabilities (no migration required)

- **Parents accept child inputs.** `parent.handle(childInput)`, or a grandchild's input, type-checks without casts and dispatches at runtime.
- **`bubbles` declarations.** An FSM can declare inputs it fires at itself but never handles: `bubbles: ["phaseComplete"]`. Declared bubbles join its typed input union, and any config mounting the FSM via `_child` must handle them, re-declare them in its own `bubbles`, or include a `"*"`. Otherwise the config fails to compile, and the error states what's missing. See [Hierarchical States](/guide/hierarchical/#declaring-bubbled-inputs).
- **Readable compiler errors.** Rejected `handle()`/`transition()` calls show the flat list of valid names (`'"go" | "stop"'`).

One sharp edge on the new `bubbles` property: the explicit-both call form (`createBehavioralFsm<Client, typeof states>`) turns inference off for the trailing type parameters, so combining it with `bubbles` requires all four type arguments spelled out. The curried form (the recommended one) and the zero-argument form are unaffected.

## Class generic signatures

`Fsm` and `BehavioralFsm` gained a fourth type parameter, `TBubbles`, defaulting to `never`. Existing three-argument annotations (`Fsm<Ctx, States, Inputs>`) still resolve unchanged. A new `BubblesOfInstance` extractor joins the existing instance-type utilities.
